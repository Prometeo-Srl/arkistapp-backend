Map of the domains

Every domain hangs off companies: it is the tenant root and the hinge of data isolation. users crosses it from the outside, because one person can belong to several tenants at once.

Tenancy and identity

One users table for everyone: super admins, company owners and workers. A role is not a property of the person but of their relationship with a tenant, and it lives on company_memberships.

Two permission axes, kept apart

AxisWhere it livesWhat it decides
org_roles membership_roles Safety roles under D.Lgs 81/08: employer, RSPP, ASPP, occupational physician, RLS, manager, supervisor, worker. Nine entries, static seed, with appointment and revocation dates.
is_admin company_memberships Application permission: invites, associates, manages collaborators' permissions. Whoever registers the company is an administrator even when they are not the employer.
Why not one single role field

The two sets change for different reasons. Safety roles are dictated by company appointments and by law; account administration is decided by whoever pays. A supervisor is not an administrator by virtue of the appointment, and an administrator may hold no org chart role at all.

Company subscription taking over

Coverage rule, one single query

At least one active workspace of the user — personal or company — holds a subscription in state trialing, active or past_due. No hierarchy of cases to keep aligned by hand.

Deliberately not implemented

Reactivating the individual plan when the worker leaves the company. The notes do not ask for it and it touches a payment, so the decision belongs to the client. The data needed is already there — superseded_by_id records which subscription absorbed which.

Document archive

Three levels, as in the prototypes: category, folder, file. Folders nest. Every file keeps its successive versions, and the expiry date is not typed in — the document type computes it.

Dynamic expiry dates

expires_at = issued_at + document_types.validity_months, recalculated on every save of the file — so it holds for the bulk certificate import too, not only for manual uploads. An expiry date set by hand is never overwritten. Fire safety 60 months, first aid 36, supervisor refresher 24, medical examination 12.

Sharing and acknowledgements

A single table carries all the sharing in the prototypes: what gets shared is polymorphic (category, folder or file), and the recipient can be a person or an org chart role — "share with every supervisor" without any group tables.

Acknowledgement bound to the version

The unique constraint is on (file_version_id, user_id), not on (file_id, user_id): a new version of the document requires a new confirmation. This is the point where the traceability the specification asks for actually survives an external inspection.

Checklists

The company prototype spends more than forty screens on the checklist builder: sections, questions of seven types, options with images, drag & drop reordering. Structure and submissions sit on separate branches.

is_non_conformity on the option is the hook needed later: it is what turns a submitted answer into an automatically detected non-conformity, with no need to re-read the answer text.

Incidents and reports

One entity for near misses and injuries alike: the same fields, the same review, separate lists in the interface. The prototypes' forty-day threshold is not a convenience filter, it is the split the register requires.

Anonymity enforced in the model

With is_anonymous set, reported_by_id is cleared before the write rather than hidden on read. The specification promises the worker an anonymous report: if the identity reached the database, that promise would depend on every future query remembering to exclude the column.

Activities, notifications, audit

"Monitora attività" is the screen both prototypes filter and paginate. It is a materialized table rather than a view: the data would be derivable, but sorting and filtering across three different sources is not worth paying for on every open.

  • Three sources, one list: a missing acknowledgement, an assigned checklist, an expiring certificate. The subject_type column says which.
  • Notifications: schema aligned with DatabaseNotification, so Laravel's database channel works with no custom layer, plus the domain columns (tenant, channel, subject).
  • Audit: the specification requires every upload, change and access to be tracked. changes keeps the delta, not just the fact.

Support

Chat, email and call are the same thread on different channels. A call leaves the metadata only: the prototype opens the system dialer, so the telephony never goes through the platform.

Open questions

Three decisions still belong to the client, plus one already settled. None of them needs a schema change: they are product choices, and the model holds either answer.

QuestionThe conflictWhat changes
Reactivating the individual plan A worker leaves the company: does their personal plan come back, or must it be re-subscribed? A job. The data already sits in superseded_by_id
Acknowledgement signature The prototypes only show a tap confirmation signature_path stays nullable
One user across several companies "Cambio profilo" implies an external consultant following more than one company Already modelled; confirm it as a requirement
Worker permissions — settled The specification grants read-only access; the worker prototype has folder creation and file upload The prototypes win. Policy only: an editor grant on the personal folder, read-only elsewhere
The specification contradicts itself

The same document states that clients get "accesso in lettura e scrittura ai propri documenti" and, a few lines below, that a client "non avrà alcuna possibilità di modifica dei contenuti". The prototypes are more recent and show full write access, and the client has confirmed the prototypes take precedence.
